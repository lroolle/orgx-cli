* [2026-01-06] Markdown Stable IDs + Safe Title Writes                 :BREAKING:RELIABILITY:
:PROPERTIES:
:ID: devlog-2026-01-06-markdown-stable-ids
:END:

** Context
orgx-cli needs stable refs (=::ID:=) for safe, repeatable edits; Markdown previously only had hash refs (=::H:=) and line addressing was inconsistent.

** Why
Hash refs in Markdown are fragile and Markdown spans were byte offsets, which blocked safe line-scoped writes (=orgx set= hard-disabled Markdown writes).

** What
- =BREAKING= Standardized Markdown =span= to 1-based line numbers (like Org) in JSON IR
- Markdown headings can carry stable IDs via adjacent marker: =<!-- orgx-id: <id> -->=; parser emits =path::ID:<id>= and populates =props.ID=
- =orgx id ensure= supports Markdown by inserting the marker right after the heading (Org behavior unchanged: PROPERTIES drawer + =:ID:=)
- =orgx id list= / =orgx id check= scan =.org= and =.md= files
- Enabled Markdown writes for =orgx set= and =orgx heading set= (title changes only, requires =::ID:= ref)

** Context
orgx-cli is a Go CLI tool for working with org-mode and markdown files, inspired by gh-cli's design. Context-efficient interface for LLMs to work with structured documents.

** Why
NAK code review identified critical bugs in =set= command: non-TTY safety gate missing, fuzzy heading matching, non-deterministic tag sorting, global string replacement causing corruption.

** What
- =BREAKING= Non-TTY safety: writes require =--yes= in non-interactive mode (pkg/cmd/set/set.go, pkg/cmd/heading/set/set.go)
- =RELIABILITY= Position-based heading lookup using =Span.Start= from parser instead of =strings.Contains= (pkg/cmd/heading/shared/lookup.go)
- =RELIABILITY= Line-based editing at specific index instead of =strings.Replace= (pkg/cmd/set/set.go, pkg/cmd/heading/set/set.go)
- Tag sorting with =slices.Sort()= for deterministic output (pkg/cmd/heading/set/set.go)
- Removed misleading =--fields= flag that was accepted but non-functional (pkg/cmdutil/json_flags.go)
- Fixed loose ref matching: =strings.Contains= → =strings.HasSuffix= (pkg/cmd/heading/shared/lookup.go)
- Added ~/path expansion via new =ExpandPath()= helper (pkg/cmd/heading/shared/lookup.go)
- Eliminated double file reads: new =ParseFileContent()= and =FindHeadingFromContent()= (pkg/parser/parser.go)

** How

** Notes
*** Assumptions
- go-org library uses 1-based line numbers (confirmed via testing)
- Markdown parser stores byte offsets in =Span=, not line numbers (known limitation)
- org files are primary use case; markdown support secondary

*** Constraints
- Must maintain zero external runtime dependencies (stdlib + go-org + goldmark only)
- Must preserve exact file formatting (whitespace, comments, non-heading content)
- Output must be deterministic for agent parsability

*** Open Questions
- Should =orgx id ensure= generate UUIDs or short hashes? (UUIDs chosen for org-roam compat)
- How to handle ID conflicts across files? (Error on duplicate, let user resolve)
- Markdown heading hash stability: include children in hash? (Yes, for stability)

*** Gotchas
- go-org AST uses 1-based line numbers, Go file I/O uses 0-based indexing
- Duplicate heading titles break title-based matching (now fixed with position-based)
- Map iteration order is random in Go (tags now explicitly sorted)
- =strings.Replace(s, old, new, -1)= replaces ALL occurrences (now line-scoped)

** Architecture: Core Contracts Established
*** Five Immutable Rules
1. =READS NEVER WRITE= - no implicit mutations during get/peek/find
2. =WRITES ARE EXPLICIT= - require =--yes= in non-interactive mode
3. =REFS HAVE POLICIES= - stable (::ID:) vs fragile (::/path, ::H:hash)
4. =OUTPUT IS DETERMINISTIC= - sorted, stable schema, no randomness
5. =GRAMMAR IS NOUN-VERB= - =orgx <noun> <verb>= with legacy aliases

*** Ref Stability Hierarchy
| Level     | Pattern              | Example                    | Write Policy      |
|-----------+----------------------+----------------------------+-------------------|
| STABLE    | =path::ID:<uuid>=    | =file.org::ID:abc-123=     | Safe, encouraged  |
| FRAGILE   | =path::/outline=     | =file.org::/Proj/Design=   | Warn, allow       |
| FRAGILE   | =path::H:<hash>=     | =README.md::H:a1b2c3=      | Warn, allow       |
| AMBIGUOUS | bare path            | =file.org=                 | Error, reject     |

* [2026-01-08 Wed] Design Direction: Agent-First Timestamp & State Management

** Context

Discussion on how to handle timestamps and state management in orgx.
Explored org-roam, org-agenda, Logseq as inspiration.

** Decision

Agent-first, not human-UI-first.

- orgx = CLI for agents (token-efficient, composable)
- Logseq = inspiration for concepts, not a dependency
- Build for agent-to-agent orchestration
- Human in the loop, but agents do the orchestration

** Key Concepts from org-agenda/org-roam/Logseq

- State transitions: IDEA → TODO → STRT → DONE (with WAIT/HOLD)
- Timestamps: SCHEDULED, DEADLINE, CREATED, CLOSED
- State change logging: LOGBOOK drawer
- Daily notes pattern: date-scoped files
- Block/heading linking: stable refs

** TODO States (user's Emacs config)

IDEA  - captured, not actionable
TODO  - committed, ready to work
PROJ  - project container
LOOP  - recurring
STRT  - actively working
WAIT  - blocked on external
HOLD  - paused intentionally
DONE  - completed
KILL  - cancelled

** Proposed Features

1. State change logging (auto-append to LOGBOOK)
2. Timestamp flags (--scheduled, --deadline, --created)
3. State-aware queries (--todo WAIT, --after DATE)
4. Capture command (orgx capture "text" --to FILE)
5. Promote/refile (orgx promote ref --to FILE)
6. Log/history view (orgx log ref)
