#+TITLE: Tree-sitter Evaluation for orgx-cli Parser
#+DATE: [2026-01-05]
#+FILETAGS: :devlog:research:arch:

* Summary

** Context
orgx-cli (Go CLI for LLM Org/Markdown ops) uses go-org + goldmark batch parsers with custom IR.

** Why
Evaluate tree-sitter for incremental parsing, precise position tracking, and source-preserving edits vs current batch-only go-org implementation.

** What
- Research tree-sitter core tech, Go bindings, org-mode grammar maturity
- Benchmark potential gains: incremental parse (1ms vs full reparse), 36-50x speedups observed in other langs
- Identify blockers: grammar maturity (all WIP/archived), CGO overhead, dynamic org keyword support

** How
*** Current Parser Stack
| Component | Lib | Capabilities | Limitations |
|-----------+-----+--------------+-------------|
| Org | =github.com/niklasfasching/go-org= | Headlines, props, scheduling, 80/20 org spec | No incremental, batch-only, manual line tracking |
| Markdown | goldmark | Full GFM | Batch-only |
| IR | Custom | Unified doc structure | Re-parse on edit |

*** Parser Location
#+BEGIN_SRC bash
pkg/parser/org.go  # Wraps go-org with lineTracker hack for spans
#+END_SRC

*** Tree-sitter Capabilities
1. Incremental parsing: edit 1 line → reparse ~1ms (vs full file)
2. Built-in positions: byte offsets + 0-based row/col
3. Query language: S-expression pattern matching
4. Error recovery: partial trees on syntax errors
5. CST: preserves all tokens including whitespace

*** Go Binding Options

| Community | =github.com/smacker/go-tree-sitter= | More grammars bundled, requires CGO |

Both require explicit =Close()= calls (CGO finalizer bugs).

*** Constraints

*** Gotchas
- tree-sitter positions are 0-based (row, col)
- go-org has no built-in position tracking (we use lineTracker workaround)
- Tree-sitter grammars can't express org's per-file keyword config (=#+TODO:=)
- All Go tree-sitter bindings leak memory without explicit =Close()=

*** Path Forward (Revisit Q2 2026)
1. If tree-sitter-org grammar reaches 1.0 → prototype hybrid parser
2. If live-editing requested → justify CGO overhead with benchmarks
3. Otherwise: optimize go-org path, cache parse trees in-memory

** Actionable Alternatives (Short-Term)

*** Option 1: Improve lineTracker (Current)
Current =lineTracker= in =pkg/parser/org.go= scans lines sequentially.

Optimizations:
- Pre-build line offset index: O(n) once, O(1) lookup
- Use string matching with heading prefix (=***=) for faster scan
- Cache parsed results per file (keyed by SHA256)

#+BEGIN_SRC go
type lineIndex struct {
    offsets []int  // byte offset of each line start
    lines   []string
}

func (idx *lineIndex) LineAt(offset int) int {
    return sort.Search(len(idx.offsets), func(i int) bool {
        return idx.offsets[i] > offset
    })
}
#+END_SRC

*** Option 2: Fork go-org with Position Tracking
Emacs org-element tracks these properties (from =org-element-api.org=):
- =:begin=, =:end= - element boundaries
- =:contents-begin=, =:contents-end= - inner content
- =:post-affiliated=, =:post-blank= - precise positions

Fork strategy:
1. Add =Begin int=, =End int= fields to each Node type
2. Modify lexer to track byte positions during tokenization
3. Propagate positions through parse tree construction

Effort: ~2-3 weeks, ongoing maintenance burden.

*** Option 3: Hybrid Pre-parser
Use simple regex/scanner to extract positions, go-org for semantics:

#+BEGIN_SRC go
// Fast heading scanner (positions only)
var headingRe = regexp.MustCompile(`(?m)^(\*+)\s+(.*)$`)

func scanHeadings(content []byte) []HeadingPos {
    matches := headingRe.FindAllSubmatchIndex(content, -1)
    // Returns line positions without semantic parsing
}

#+END_SRC

Pros: No fork, composable, fast position lookup
Cons: Two-pass parsing, potential sync issues
